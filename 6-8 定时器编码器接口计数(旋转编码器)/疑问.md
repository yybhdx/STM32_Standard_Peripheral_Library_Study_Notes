# 关于 STM32 定时器编码器接口（计数/位置测量）的疑问解答与学习笔记

### 1. “编码器计数”与“编码器测速”的核心区别是什么？

| 比较维度 | 编码器计数 (本项目) | 编码器测速 |
| :--- | :--- | :--- |
| **应用目的** | 测量电机的**累计位置、总位移或转过的角度**。 | 测量电机的**实时旋转速度**。 |
| **CNT 是否清零** | **否**。CNT 寄存器一直累加或累减，不进行手动清零。 | **是**。每隔一段固定的时间（如1秒），读取 CNT 后必须将其清零。 |
| **`Encoder_Get` 逻辑**| 直接返回 `TIM_GetCounter(TIM3)`。 | 读取 `TIM_GetCounter(TIM3)`，然后调用 `TIM_SetCounter(TIM3, 0)` 清零并返回读出的值。 |
| **数据含义** | 读取出的数值代表**从启动开始，编码器旋转积累的总增量（位移）**。 | 读取出的数值代表**在单位时间内编码器转过的脉冲数（速度）**。 |

---

### 2. 计数项目中的 CNT 溢出与数据表示范围是怎样的？

在本项目中，定时器3的自动重装值（ARR）配置为最大的 `65535`，这为计数器提供了最大的变化量程。
* **物理计数器 (CNT)**：由于定时器是 16 位的，`CNT` 的值在物理上只在 `0 ~ 65535` 之间循环。
* **软件有符号转换 (int16_t)**：在 `Encoder_Get` 中，我们将 CNT 的无符号 16 位值强制转换为**有符号的 16 位整数 (`int16_t`)** 返回：
  * **正向旋转（右转）**：计数值从 `0` 开始递增：`0 -> 1 -> 2 -> ... -> 32767`。如果继续正转，数值会发生溢出，并突变为 `-32768 -> -32767 -> ... -> -1 -> 0`。
  * **反向旋转（左转）**：计数值从 `0` 开始递减：`0 -> -1 -> -2 -> ... -> -32768`。如果继续反转，数值会发生下溢，并突变为 `32767 -> 32766 -> ... -> 0`。

> [!TIP]
> 如果要测量超出 $\pm 32768$ 范围的长距离总位移，我们需要在软件中开启定时器的**更新中断（Update Interrupt）**，在中断服务程序中统计 CNT 向上或向下溢出的次数，从而在软件层面拼接成一个 32 位甚至 64 位的累计位移变量。

---

### 3. 时基单元中的 PSC 和 ARR 参数在“计数”中起到什么作用？

* **预分频器 (PSC)**：配置为 `1 - 1 = 0`（即不分频）。由于在编码器接口模式下，外部引脚输入信号的正负边沿直接驱动 CNT 计数，硬件会绕过预分频器，因此 **PSC 的设置对实际编码器计数没有分频效果**。
* **自动重装器 (ARR)**：配置为 `65535`。它决定了 CNT 寄存器的**最大计数上限（量程）**。在不通过更新中断统计溢出次数的前提下，ARR 应始终设为最大值，以提供尽可能大的不溢出测量范围。

---

### 4. 软件反转计数方向的实现方法
如果实际测试中发现编码器的计数方向相反（例如正转时数字减小，反转时数字增大），有以下两种解决方法：
1. **硬件调整**：将输入到单片机引脚的 A 相和 B 相两根物理信号线对调。
2. **软件调整**：修改初始化函数 `TIM_EncoderInterfaceConfig`，将其中**任意一个**通道的输入极性反相（例如将 `TIM_ICPolarity_Rising` 修改为 `TIM_ICPolarity_Falling`）。如果两个极性同时反相，则方向依然保持不变。

---

### 5. 当运行时间足够长时，CNT 不会超过 ARR 从而被清零吗？

**会，绝对会！一旦电机转动的总增量超过了 ARR（在本项目中为 65535），计数器确实会发生溢出并回零，这是硬件计数器的物理特性。**

我们来拆解这个过程以及实际开发中的解决办法：

#### 1) 硬件和软件上的溢出表现

* **硬件层面（无符号 16 位寄存器）**：
  * **正转**：当 CNT 计数到 `65535` 后，如果再来 1 个正向脉冲，CNT 就会溢出重装为 `0`。
  * **反转**：当 CNT 递减到 `0` 后，如果再来 1 个反向脉冲，CNT 就会下溢重装为 `65535`。
  
* **软件层面（强制转换为有符号数 `int16_t`）**：
  * 因为在代码中我们使用了 `(int16_t)` 转换，所以在软件输出上，溢出突变点**并不是在 65535 $\rightarrow$ 0**，而是在**半量程处**：
    * **正转突变**：当计数值从 `32767` 增加到 `32768` 时，软件读数会突然从 **`32767` 跃变为 `-32768`**。
    * **反转突变**：当计数值从 `-32768` 减少到 `-32769`（物理上是 32767）时，软件读数会从 **`-32768` 跃变为 `32767`**。
  * **特别注意**：硬件的 `65535` 到 `0` 的翻转，在有符号数看来是 `-1` 变到 `0`，所以在 $0$ 附近穿过时，软件读数是**完全平滑且连续的**。

---

#### 2) 实际应用中如何解决这个限制？

如果你的应用场景只是一台旋转范围受限的设备（比如云台舵机只在 $0 \sim 360^\circ$ 内转动，一圈脉冲数远小于 32767），那么这个溢出不会触发，直接读取即可。

但如果要测高速电机或传送带的**长期累计位移**，我们就必须在软件中引入**“溢出中断统计法”**来扩展计数器的位数（从 16 位扩展到 32 位甚至 64 位）：

* **解决步骤**：
  1. **配置中断**：开启 TIM3 的**更新中断（Update Interrupt）**。
  2. **软件定义大变量**：在内存中定义一个 32 位的有符号累加器变量，例如 `int32_t TotalPosition = 0;`。
  3. **在中断中判断方向并累加**：
     当定时器发生溢出中断时，硬件会自动向 CPU 申请中断。在中断服务程序（`TIM3_IRQHandler`）中，我们读取定时器的计数方向标志位（通过寄存器 `TIMx_CR1` 的 `DIR` 位）：
     * 如果是**向上溢出**（从 65535 到 0）：说明正转走完了一圈，`TotalPosition += 65536;`
     * 如果是**向下溢出**（从 0 到 65535）：说明反转退回了一圈，`TotalPosition -= 65536;`
  4. **计算最终绝对位置**：
     当我们需要获取绝对位置时，最终的位移公式为：
     $$\text{绝对位置} = TotalPosition + \text{当前读取的 CNT 值}$$
     通过这种方法，可测量的计数值量程将扩展为 $-2,147,483,648 \sim 2,147,483,647$，对于任何物理电机来说，这都相当于**无限长**，再也不会受到 65535 的量程限制了。

---

### 6. 初始化结构体中的 TIM_ICInitStruct.TIM_ICPolarity 参数是不是真的没有影响？

**是的，这个参数在实际运行中完全没有影响，它在后面被完全覆盖了。**

我们可以从以下两个步骤来分析为什么它不起作用：

#### 1) 为什么它会被覆盖？
在 [Encoder.c](file:///D:/Project/STM32/Jiangxie%20TechnologySTM32/STM32_Standard_Peripheral_Library/6-8%20%E5%AE%9A%E6%97%B6%E5%99%A8%E7%BC%96%E7%A0%81%E5%99%A8%E6%8E%A5%E5%8F%A3%E8%AE%A1%E6%95%B0(%E6%97%8B%E8%BD%AC%E7%BC%96%E7%A0%81%E5%99%A8)/Hardware/Encoder.c) 的初始化过程中，我们执行了两个动作：

1. **第一步（通过结构体配置输入捕获）**：
   调用 `TIM_ICInit(TIM3, &TIM_ICInitStruct)`。这会把结构体中的 `TIM_ICPolarity_Rising` 写入定时器的通道极性寄存器。
2. **第二步（配置编码器接口）**：
   紧接着调用了库函数：
   ```c
   TIM_EncoderInterfaceConfig(TIM3,
                              TIM_EncoderMode_TI12,
                              TIM_ICPolarity_Rising,  // 通道 1 极性
                              TIM_ICPolarity_Rising); // 通道 2 极性
   ```
   **核心原因**：`TIM_EncoderInterfaceConfig` 这个函数内部会重新配置通道 1 和通道 2 的输入极性，并**直接覆盖掉**刚才 `TIM_ICInit` 写入的值。

因此，无论你在第一步中将 `TIM_ICInitStruct.TIM_ICPolarity` 设为 `Rising`、`Falling`，还是由于调用了 `TIM_ICStructInit` 使用了默认值，**最终定时器所使用的极性都完全取决于 `TIM_EncoderInterfaceConfig` 的第 3 和第 4 个参数**。

---

#### 2) 那为什么初始化时还要写它呢？
通常，在编写底层驱动时有以下几个原因会保留这行代码：
* **结构体初始化的严谨性**：为了保证 `TIM_ICInitStruct` 这个结构体所有的成员都有一个明确的初始值，防止内存中的随机数导致外设配置出错（尽管在前面调用了 `TIM_ICStructInit` 已经赋予了默认值）。
* **代码可读性**：向阅读代码的人展示这一通道在输入捕获阶段设置的是默认的极性（不反相）。
* **完全可以删除**：事实上，在调用了 `TIM_ICStructInit(&TIM_ICInitStruct)` 之后，这行赋值语句 `TIM_ICInitStruct.TIM_ICPolarity = TIM_ICPolarity_Rising;` **完全可以删掉**，对程序运行结果不会产生任何影响。真正起作用的极性配置在最后的 `TIM_EncoderInterfaceConfig` 函数中。
